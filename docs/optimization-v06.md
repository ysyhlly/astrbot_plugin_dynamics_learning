# v0.6.0 学习调度与审查工作台

## 增量学习

持久化收件队列使用自增序号与每回合处理边界，先按回合合并再选批次。按最早未处理回合读取，模型输入预算不足时只提交实际输入的连续部分。提案和处理进度在同一SQLite事务内提交；模型失败、状态失效或事务失败均保留待处理数据。模型运行期间新到的回调不会被本批标记完成，晚到的结果作为该回合的新更新继续分析。

升级沿用旧版本已有的完成边界。旧版没有保存每批完整输入清单，无法可靠判断历史上哪些内容被其“最近80条”窗口略过，因此不会凭猜测自动重放旧好感度或已完成数据。升级后的每批会记录输入事件ID、处理回合边界与回调数量，便于核对。

原始消息仍按保留天数清理，但未分析回调及其引用的原始来源保留至完成；手动删除会话会一并删除收件队列和来源。已处理的旧队列与批次日志随保留周期清理。

## 模型调用不占用采集锁

短锁内准备证据快照；锁外调用模型；提交时重新核对删除代数、当前角色、资料版本与模型绑定。不同群可推进，同一群的分析串行，分析和审查共用最多2个模型并发槽位。自动调度每轮先为不同群各处理一批，最多4轮追赶；少量消息等满一个检查间隔后也会处理。失败群本轮不反复调用模型，待后续检查重试。

审查等待模型时允许人工拒绝、修改与删除；模型返回必须通过原提案更新时间校验。不会用迟到结果覆盖人工决定。

## 原话候选质量

优先明确引用；明确提及前一位成员也可作为候选关联。仅相邻消息须有足够词面话题关联，且同一成员的相同回应在至少两个独立来源、相隔至少60秒时重复出现。短促通用应答、链接、代码和疑似联系方式不作为可复用表达样例。关联规则只是筛选，保留独立LLM审查与人工确认。

该规则用于生成新候选，既有待审内容保留原状态，不自动取消或批准。

## 审查工作台

待处理内容按完整群会话、角色版本、成员分组，提供全量组目录与每组分页，避免最新记录窗口遮住较早待审内容。支持类别筛选、调整前后对比和一次最多20条的显式选择。提交前弹出核对清单，只有用户点击确认才发送批准请求。

批量操作只允许同一群、角色和成员，沿用每项原定及当前审查要求，检查记录与目标版本。任何一条冲突整批回滚；每个成功项目仍保留独立审计和回滚记录。部署不会代替人工批准已有记录。好感度继续自动生效，固定性格约束不变。
