# 审计修复验证说明

## 页面请求与证据

- 策略写入后使策略列表及概览的请求世代失效，旧 GET 响应不能覆盖页面；写后刷新等待并重新请求。写请求携带列表中的 revision，供服务端检测状态冲突。
- 导入或分析完成后，同样等待已进行的全局刷新结束，再读取新快照。
- 评测及迭代页面按证据区分宿主有效基线、默认参考基线和未知来源，并显示服务端提供的报告过期标记。策略详情显示过期证据说明。
- Shadow 页面按完整实验身份展示独立门槛、标注数、分歧及净收益；旧记录总览不可作为晋级依据。
- JSON 导出标为诊断用途，明确不能用于恢复策略和状态。

## 核心修复

- 综合验证对每个最终候选使用同一份冻结参数，并在生成候选前隔离会话与时间验证集。迭代的选择数据不再充当最终测试集；关闭 tuning 也走统一收尾。
- 数据摘要覆盖实际样本内容。候选记录包含参数、基线、数据和切分身份；保存及人工晋级检查证据一致性。有效基线来自已加载宿主的白名单配置读取接口，无法读取时明确为默认参考。
- 完整会话快照包含空会话，未知、损坏或截断会话不替换；裸记录按消息增量修订。数据变化标记报告与策略过期并撤回候选供给；初始化也使旧版缺证据策略过期。
- 策略变更与重置共用互斥锁。expected_revision 冲突返回 HTTP 409；发布日志能在下一次读取恢复中断写入，三份发布记录带同一 revision。该机制不是多进程数据库事务。
- 模型缓存包含数据、Provider、模型、Prompt 与解析器身份。同类在途请求合并并限制并发；重置与终止使旧请求失效。查询缓存按配置/数据世代失效，30 秒过期，计算移至工作线程。
- 同步修改相邻 ChatDynamics 副本的 learning_policy、routing_trace、shadow_telemetry 以生产和保留实验身份，保留宿主已有未提交修改。旧宿主仍可读，但缺少身份的历史 Shadow 记录只能用于总览，shadow_observed 保持保守的 False。

## 性能记录

见 [原始测量](query-benchmark.json) 和 `scripts/benchmark_queries.py`。使用 SDK/KV 替身及预载合成样本，实际执行插件查询；不代表真实宿主或旧版本对照。

5000 样本冷查询约 88–196 ms，热查询中位约 0.28–1.10 ms；48 次查询没有 KV 写入。10000 样本 quality 冷查询约 563 ms，事件循环最大迟到约 88 ms，说明工作线程仍受 Python CPU/GIL 和调度影响，不能宣称请求完全不影响事件循环。
